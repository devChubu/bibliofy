How the Internet Works

A friendly, accurate guide to understanding what really happens between clicking a link and seeing a webpage — from DNS lookups and packet switching to submarine cables and data centers. No engineering degree required.

Chapter 1 From Click to Server

~8 min read
Key question: What actually happens in the milliseconds between you clicking a link and a faraway computer receiving your request?
Prerequisite

No prior technical knowledge is needed. If you have ever used a web browser, you have enough background to follow along. We will build up every concept from scratch.

What Happens When You Type a URL

When you type www.example.com into your browser's address bar and press Enter, you kick off a chain of events that spans the entire planet — often in under a second. But your browser cannot actually send a message to "www.example.com." Computers on the internet do not communicate using human-readable names. They communicate using numerical addresses called IP addresses, which look something like 93.184.216.34.

Think of it like mailing a letter. You might say "send this to Grandma's house," but the postal service needs a street address with a zip code. Similarly, your browser needs the numerical IP address that corresponds to the name you typed. The system that translates names into numbers is called the Domain Name System, or DNS.

Key Concept: IP Addresses

An IP (Internet Protocol) address is a unique numerical label assigned to every device connected to the internet. IPv4 addresses use four numbers separated by dots (e.g., 192.168.1.1), giving about 4.3 billion possible addresses. Because the internet outgrew that limit, IPv6 was created, using longer hexadecimal addresses (e.g., 2001:0db8:85a3::8a2e:0370:7334) that provide a practically unlimited supply.

DNS: The Internet's Phone Book

The Domain Name System is often called "the phone book of the internet," and the analogy is remarkably apt. Just as you once looked up a person's name to find their phone number, DNS lets your computer look up a domain name to find its IP address. This lookup process is called DNS resolution, and it involves a conversation between your computer and several specialized servers.

Here is what happens, step by step:

  1. Browser cache check — Your browser first checks if it recently looked up this domain. If so, it already knows the IP address and skips ahead.
  2. Operating system cache — If the browser cache misses, the OS checks its own DNS cache.
  3. Recursive resolver — If neither cache has the answer, the request goes to a recursive DNS resolver (usually run by your ISP or a service like Cloudflare's 1.1.1.1 or Google's 8.8.8.8).
  4. Root nameserver — The resolver asks a root nameserver, "Who handles .com domains?" The root server points to the .com TLD (Top-Level Domain) servers.
  5. TLD nameserver — The resolver asks the .com TLD server, "Who handles example.com?" It gets pointed to the authoritative nameserver for example.com.
  6. Authoritative nameserver — Finally, this server answers with the actual IP address: 93.184.216.34.
Figure 1.1 — DNS resolution: the recursive resolver queries root, TLD, and authoritative nameservers on your behalf.

You can see this process yourself. Open a terminal and run a DNS lookup:

bash
# Look up the IP address for a domain
nslookup www.example.com

# More detailed output showing the full resolution chain
dig www.example.com +trace

# On Windows, you can also use:
nslookup -type=A www.example.com 8.8.8.8
Try these commands in your own terminal to see DNS resolution in action.
Try It Yourself

Open your browser's developer tools (press F12), go to the Network tab, and reload any page. Look at the "Timing" section for any request — you will see a "DNS Lookup" phase. For frequently visited sites, this will show 0 ms because the result is cached. For a brand new domain, it can take 20–120 ms.

Routers and the Path Forward

Once your computer knows the IP address, it needs to send a message to that address. But the destination server is rarely on the same network as your computer. Your request must travel through a series of intermediate devices called routers. Each router is like a post office sorting facility — it reads the destination address on your message and forwards it one step closer to its goal.

This process is called routing, and each step along the way is called a hop. A typical web request might pass through 10–20 routers between your computer and the destination server. Each router uses a routing table — essentially a set of rules that says "for addresses in this range, forward to that next router."

No Guaranteed Path

The internet has no single fixed route between two points. If a router or cable fails, traffic is automatically rerouted through a different path. This is a core design principle: the internet was built to survive partial failures. Two requests to the same server, sent seconds apart, may take completely different paths across the network.

bash
# Trace the route from your computer to a server
# Each line is one "hop" through a router
traceroute www.example.com

# On Windows, use:
tracert www.example.com

# Example output:
#  1   1 ms    <1 ms   <1 ms   192.168.1.1       (your home router)
#  2   8 ms     7 ms    8 ms   10.0.0.1            (ISP local)
#  3  12 ms    11 ms   12 ms   72.14.215.85        (ISP regional)
#  4  18 ms    17 ms   18 ms   108.170.252.129     (backbone)
#  ...
# 11  24 ms    23 ms   24 ms   93.184.216.34       (destination)
The traceroute command reveals every router your data passes through on its way to the destination.
Key Takeaway

Clicking a link triggers three key steps: (1) your browser uses DNS to translate the domain name into an IP address, (2) your request is packaged with that destination address, and (3) routers relay it hop-by-hop across the network until it reaches the server. All of this typically happens in under 100 milliseconds.

Chapter 2 Protocols — The Language of the Web

~10 min read
Key question: How do two computers that have never met before agree on a way to communicate, and how do they keep that conversation private?
Prerequisite

This chapter assumes you understand what an IP address is and how DNS resolution works. If those terms are unfamiliar, start with Chapter 1: From Click to Server.

HTTP: Request and Response

Once your browser knows where to send its message (thanks to DNS), it needs a language to speak. That language is HTTP — the HyperText Transfer Protocol. HTTP is a simple, text-based conversation between your browser (the client) and the web server. The client sends a request, and the server sends back a response.

An HTTP request has a few key parts: a method (what you want to do), a path (which resource you want), and headers (extra information about the request). Here is what one looks like:

text
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html
Accept-Language: en-US
Connection: keep-alive
An HTTP GET request — your browser sends something like this every time you visit a page.

The server processes this request and sends back a response:

text
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Date: Wed, 16 Oct 2026 12:00:00 GMT

<!DOCTYPE html>
<html>
  <head><title>Example</title></head>
  <body><p>Hello, world!</p></body>
</html>
An HTTP response — the status code 200 means "OK, here's what you asked for."
Key Concept: HTTP Methods

GET asks to retrieve a resource (loading a page). POST sends data to the server (submitting a form). PUT replaces a resource, and DELETE removes one. The vast majority of everyday web browsing uses GET requests — your browser is simply asking "give me this page."

The three-digit status code in the response tells you what happened. You have probably encountered some of these:

Code Meaning When You See It
200 OK Everything worked — here is the page you requested
301 Moved Permanently This page has moved to a new address; your browser is redirected automatically
404 Not Found The page does not exist — you probably have a typo in the URL
500 Internal Server Error The server crashed or has a bug — not your fault
503 Service Unavailable The server is overloaded or down for maintenance

TCP: Reliable Delivery

HTTP tells the computers what to say, but it does not handle how the message gets there reliably. That job falls to TCP — the Transmission Control Protocol. TCP sits one layer below HTTP and guarantees that your data arrives complete, in order, and without errors.

Here is the problem TCP solves: a web page might be 2 MB in size, but the internet moves data in small chunks called packets, each only about 1,500 bytes. A 2 MB page must be split into roughly 1,400 packets. These packets may travel different routes, arrive out of order, or get lost entirely. TCP handles all of this.

Before any data is exchanged, TCP establishes a connection using a process called the three-way handshake:

Figure 2.1 — The TCP three-way handshake: SYN, SYN-ACK, ACK. Both sides confirm they can send and receive before any data flows.
Analogy: The Phone Call

The three-way handshake is like starting a phone call. You dial (SYN), the other person says "Hello?" (SYN-ACK), and you reply "Hi, it's me" (ACK). Only then do you start the actual conversation. If any of those steps fails — you get a busy signal, or they do not pick up — no call is established.

After the connection is open, TCP splits your data into numbered packets. The receiving end sends back acknowledgments for each packet it receives. If a packet goes missing, the sender retransmits it. When all packets arrive, TCP reassembles them in the correct order and hands the complete data to the application (your browser).

Protocol Layer Job Guarantees
HTTP Application Defines the conversation (request/response) Structured message format
TCP Transport Reliable delivery of bytes In-order, error-checked, retransmission
IP Network Addressing and routing Best-effort delivery (no guarantees)
Ethernet/Wi-Fi Link Physical transmission on local network Hop-by-hop frame delivery
Deep Dive: What Happens When a Packet Gets Lost?

TCP uses several mechanisms to detect and recover from packet loss:

  • Sequence numbers — Every packet is numbered, so the receiver knows if one is missing (e.g., got packets 1, 2, 4 — where is 3?).
  • Acknowledgments (ACKs) — The receiver sends back the sequence number of the next packet it expects. If the sender does not receive an ACK within a timeout period, it resends the packet.
  • Duplicate ACKs — If the receiver gets packet 4 but is still waiting for packet 3, it sends another ACK for packet 3. After three duplicate ACKs, the sender retransmits immediately without waiting for the timeout (this is called "fast retransmit").
  • Congestion control — If many packets are being lost, TCP assumes the network is congested and voluntarily slows down its sending rate to give the network time to recover.

TLS/HTTPS: Encryption

Plain HTTP sends everything as readable text. Anyone who can intercept the traffic — a hacker on the same Wi-Fi network, a compromised router, or a nosy ISP — can read everything: passwords, credit card numbers, personal messages. This is where TLS (Transport Layer Security) comes in.

When you see https:// in your browser's address bar (and the lock icon), you are using HTTP wrapped in TLS encryption. The "S" stands for "Secure." TLS creates an encrypted tunnel between your browser and the server. Even if someone intercepts the data in transit, all they see is random gibberish.

The TLS handshake is a negotiation that happens immediately after the TCP handshake, before any HTTP data is sent:

TCP HandshakeSYN / SYN-ACK / ACK
→

→

Figure 2.2 — HTTPS = TCP connection + TLS encryption + HTTP messages. The handshakes happen in sequence before any page content is exchanged.
Never Trust Plain HTTP

If a website asks for your password or any personal information over plain http:// (no lock icon), do not enter it. The data will travel across the internet as readable text, visible to anyone along the path. Modern browsers now warn you when visiting HTTP sites, and most reputable websites have switched to HTTPS entirely.

bash
# View the TLS certificate for a website
openssl s_client -connect www.example.com:443 -brief

# Ciphersuite: TLS_AES_256_GCM_SHA384
# Server certificate: CN=www.example.org
# Verification: OK

# In your browser: click the lock icon in the address bar
# to see the certificate details
You can inspect any site's TLS certificate from the command line or by clicking the lock icon in your browser.
Key Takeaway

Three protocols work together to deliver a web page securely: TCP ensures all the data arrives reliably, TLS encrypts it so no one can eavesdrop, and HTTP structures the conversation into requests and responses. Together, they form the HTTPS stack that powers the modern web.

Chapter 3 The Physical Internet

~9 min read
Key question: What does the internet physically look like, and how does data cross oceans and reach your home?

Submarine Cables and Backbones

People often imagine the internet as something ethereal — data floating through the cloud, traveling wirelessly between continents. The reality is far more physical and, in many ways, more impressive. Over 95% of intercontinental internet traffic travels through submarine fiber-optic cables laid on the ocean floor. These cables are roughly the diameter of a garden hose and carry pulses of laser light at nearly the speed of light itself.

As of 2026, there are over 550 active submarine cable systems spanning more than 1.4 million kilometers across every ocean. They connect continents, islands, and coastal cities, forming the literal backbone of the global internet. Some modern cables can carry over 250 terabits per second — enough to transmit the entire Library of Congress in a fraction of a second.

Key Concept: Fiber Optics

Fiber-optic cables transmit data as pulses of light through thin strands of glass. Light travels through the fiber by bouncing off the walls at very shallow angles (total internal reflection). Because light is incredibly fast and fiber has very low signal loss, a single fiber strand can carry enormous amounts of data across thousands of kilometers with minimal degradation. Each cable typically contains multiple fiber pairs, and each pair can carry many channels of light at different wavelengths simultaneously (wavelength-division multiplexing).

Figure 3.1 — A transatlantic submarine cable with optical repeaters boosting the signal every ~80 km along the ocean floor.
Cables Are Vulnerable

Submarine cables are surprisingly fragile for something the entire internet depends on. About 100–150 cable faults occur each year, most commonly caused by fishing trawlers dragging anchors or nets across the seabed, and sometimes by undersea earthquakes or landslides. When a major cable is damaged, internet traffic for entire regions must be rerouted through other cables, sometimes causing noticeable slowdowns. Repairs require specialized cable ships and can take weeks.

Data Centers and CDNs

The servers that host websites and applications live in data centers — large, purpose-built facilities that provide reliable power, cooling, and network connectivity. A large data center might house hundreds of thousands of servers, consume as much electricity as a small city, and require enormous cooling systems to prevent the equipment from overheating.

But a single data center in Virginia is not ideal for serving users in Tokyo. The physical distance introduces delay (latency), and the link can become a bottleneck. This is where CDNs (Content Delivery Networks) come in.

A CDN is a network of servers distributed around the world. When a website uses a CDN, copies of its content are stored (cached) at many locations. When you request a page, the CDN serves it from the location nearest to you, rather than from the website's origin server thousands of miles away.

Deep Dive: How CDN Caching Works

When a user in London requests a page hosted on a server in San Francisco, the CDN checks whether its London edge server already has a cached copy:

  • Cache hit — The edge server has the content and serves it immediately. Response time: ~10 ms.
  • Cache miss — The edge server does not have the content, so it fetches it from the origin server in San Francisco (or another edge that does have it), caches a copy, and serves the user. Response time: ~150 ms for the first request; subsequent requests are cache hits.

The website's developers control how long content stays cached using HTTP headers like Cache-Control: max-age=3600 (cache for 1 hour). Static assets like images, CSS, and JavaScript are cached aggressively, while dynamic pages (like your social media feed) are typically not cached or cached only briefly.

Last-Mile Delivery and ISPs

The "last mile" is a telecom industry term for the final leg of connectivity between the internet backbone and your home or office. It is often the slowest and most expensive part of the entire chain, which is why it has its own name. Your ISP (Internet Service Provider) is the company responsible for this last-mile connection.

The technology used for the last mile varies widely:

  • Fiber to the Home (FTTH) — Fiber-optic cable all the way to your house. The fastest option, with speeds from 100 Mbps to 10 Gbps. Increasingly common in cities.
  • Cable (DOCSIS) — Uses the same coaxial cable as cable TV. Typical speeds of 100–1,000 Mbps download. Shared bandwidth with neighbors.
  • DSL — Uses existing telephone copper wires. Slower (10–100 Mbps), with speed depending on distance from the telephone exchange.
  • Fixed Wireless / 5G — Uses radio signals instead of cables. Speeds vary widely depending on distance and line of sight to the tower.
  • Satellite — Reaches remote areas where no cable infrastructure exists. Historically slow and high-latency, though modern low-earth-orbit (LEO) constellations have dramatically improved performance.
bash
# Test your internet connection speed and latency
# (requires the speedtest CLI tool)

# Example output:
# Ping: 12.45 ms
# Download: 285.32 Mbit/s
# Upload: 42.17 Mbit/s

# Check your public IP and see which ISP you're using

ISPs do not just connect you to the internet — they also connect to each other. This happens at Internet Exchange Points (IXPs), physical locations where multiple ISPs and networks meet and directly exchange traffic. This peering arrangement is what makes the internet a network of networks, rather than a single centrally controlled system.

Why Your Speed Varies

Your internet speed depends on the weakest link in the chain. Even with a 1 Gbps fiber connection at home, you might experience slow loading if: (1) the website's server is overloaded, (2) a submarine cable carrying your traffic is at capacity, (3) the CDN edge near you does not have the content cached, or (4) your Wi-Fi router is a bottleneck. Speed tests measure your connection to a nearby server — real-world performance to distant servers will differ.

Key Takeaway

The internet is a physical infrastructure of fiber-optic cables (including over 550 submarine systems), data centers, CDN edge servers, and ISP networks. Data crosses oceans as pulses of light through cables on the seafloor, gets cached at CDN nodes near you for speed, and reaches your device via your ISP's last-mile connection. Understanding this physical layer explains why geography, infrastructure, and your ISP choice all affect your internet experience.
