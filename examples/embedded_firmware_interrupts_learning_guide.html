A hands-on guide to understanding hardware interrupts from the signal pin to the service routine — covering ARM Cortex-M NVIC architecture, priority management, and safe ISR coding patterns for reliable embedded systems.

Chapter 1 What Are Interrupts?

~8 min read
Key question: Why does a processor need a mechanism to stop what it is doing and respond to an external event, and what happens inside the CPU when it does?
Prerequisite

This chapter assumes you can read simple C code and have a basic understanding of CPU registers and program execution flow. No prior RTOS or ARM-specific knowledge is required.

Polling vs. Interrupts

Imagine a firmware application that must react when a user presses a button. The simplest approach is polling: the main loop repeatedly reads the GPIO pin and checks whether its state has changed.

C
/* Polling approach -- wastes CPU cycles */
while (1) {
    if (GPIO_ReadPin(GPIOA, GPIO_PIN_0) == GPIO_PIN_SET) {
        handle_button_press();
        /* debounce delay */
        delay_ms(200);
    }
    /* ... other tasks starved while we poll ... */
}

Polling is easy to understand, but it has two serious problems:

  • Wasted CPU time. The processor spends most of its cycles reading a pin that has not changed. On a battery-powered device, those cycles burn power for nothing.
  • Unbounded latency. If the main loop also handles UART reception, ADC conversion, and display updates, the button check might not run for tens of milliseconds — or longer. The user perceives the system as sluggish.

An interrupt flips the model. Instead of the software asking the hardware "has anything happened?", the hardware tells the software "something just happened — deal with it now." The CPU suspends its current work, executes a short handler called an Interrupt Service Routine (ISR), and then resumes exactly where it left off.

Key Concept: Asynchronous Event Notification

An interrupt is fundamentally an asynchronous event. It can arrive between any two instructions in your main code. This is what makes interrupts powerful — zero-latency awareness of external events — and also what makes them dangerous, because your main code must be written to tolerate being paused at arbitrary points.

Criterion Polling Interrupts
Response latency Depends on loop period (unbounded) Deterministic (hardware-guaranteed entry)
CPU utilization High — constantly checking Low — CPU runs other code or sleeps
Code complexity Simple sequential logic Requires concurrency awareness
Power consumption Cannot sleep between polls CPU can enter low-power mode between events
Best for High-frequency data (ADC streaming) Sporadic, latency-sensitive events (UART RX, GPIO)

The Interrupt Lifecycle

When an interrupt fires on an ARM Cortex-M processor, a precise sequence of hardware-managed steps occurs. Understanding this sequence is essential for writing correct firmware.

IRQ AssertedPeripheral signals CPU
→
Context SavePush R0-R3, R12, LR, PC, xPSR
→
ISR ExecutesHandler code runs
→
Context RestorePop registers, resume
Figure 1.1 — The four phases of interrupt handling on Cortex-M.

The key steps in detail:

  1. IRQ assertion. A peripheral (timer, UART, GPIO) sets its interrupt request line high. The NVIC latches the request as "pending."
  2. Context save (stacking). The hardware automatically pushes eight registers onto the current stack: R0–R3, R12, LR (link register), PC (return address), and xPSR (status register). This takes 12 cycles on Cortex-M3/M4.
  3. ISR execution. The CPU fetches the handler address from the vector table and begins executing your ISR code. Your ISR should clear the interrupt source flag and do minimal work.
  4. Context restore (unstacking). When the ISR returns (via BX LR with the special EXC_RETURN value), the hardware pops the saved registers and resumes the interrupted code as if nothing happened.
Stack Overflow Risk

Every interrupt pushes at least 32 bytes onto the stack (8 registers x 4 bytes). If you use floating-point registers, the stacking frame grows to 104 bytes. Nested interrupts multiply this. A system with 4 priority levels and FPU context can consume 416 bytes of stack just for interrupt frames — before any local variables in your ISRs. Always size your stack with worst-case nesting in mind.

Interrupt Latency

Interrupt latency is the time between the peripheral asserting its IRQ line and the first instruction of your ISR executing. On Cortex-M, this is deterministic:

Core Zero-Wait-State Latency Notes
Cortex-M0/M0+ 16 cycles Minimal core, no tail-chaining
Cortex-M3/M4 12 cycles Tail-chaining reduces back-to-back latency to 6 cycles
Cortex-M7 12 cycles Pipeline effects can add 0–2 cycles
Cortex-M33 12 cycles TrustZone transitions add latency for secure interrupts
Measuring Real Latency

Datasheet latency is best-case. In practice, add wait-states for flash access (often 1–5 cycles at higher clock speeds), bus arbitration delays if DMA is active, and any time spent in higher-priority ISRs. Toggle a GPIO pin at ISR entry and measure with an oscilloscope for ground truth.

Figure 1.2 — Interrupt latency timeline on Cortex-M3/M4 (zero wait states).
Key Takeaway

Interrupts trade code complexity for responsiveness and efficiency. They let the CPU sleep between events (saving power) and respond in deterministic time (enabling real-time behavior). The hardware handles register save/restore automatically — your job is to keep the ISR short and safe.

Chapter 2 The NVIC on ARM Cortex-M

~10 min read
Key question: How does the Nested Vectored Interrupt Controller decide which interrupt runs, and what happens when two interrupts arrive at the same time?
Prerequisite

Priority Levels and Groups

The NVIC assigns each interrupt a priority number, where a lower number means higher priority (priority 0 is the most urgent). The number of priority bits is implementation-defined: Cortex-M3/M4 typically implement 3 to 8 bits, giving 8 to 256 levels. Many STM32 devices implement 4 bits (16 levels).

ARM splits priority into two fields: group priority (also called preemption priority) and sub-priority. The Application Interrupt and Reset Control Register (AIRCR) defines where the split happens via the PRIGROUP field.

PRIGROUP Group Priority Bits Sub-Priority Bits Preemption Levels Sub-Levels
0b011 (3) [7:4] [3:0] 16 16
0b100 (4) [7:5] [4:0] 8 32
0b101 (5) [7:6] [5:0] 4 64
0b110 (6) [7:7] [6:0] 2 128

The distinction matters for preemption: only a different group priority can preempt a running ISR. Sub-priority only determines the order when two interrupts of the same group priority are pending simultaneously.

C
/* Configure NVIC priority for USART1 and TIM2 on STM32 (4-bit priority) */

/* Set priority grouping: 2 bits preemption, 2 bits sub-priority */
NVIC_SetPriorityGrouping(5);  /* PRIGROUP = 5 -> [7:6] group, [5:4] sub */

/* USART1: highest preemption priority (group 0), sub-priority 0 */
NVIC_SetPriority(USART1_IRQn, NVIC_EncodePriority(5, 0, 0));

/* TIM2: lower preemption priority (group 1), sub-priority 0 */
NVIC_SetPriority(TIM2_IRQn, NVIC_EncodePriority(5, 1, 0));

/* Enable both interrupts */
NVIC_EnableIRQ(USART1_IRQn);
NVIC_EnableIRQ(TIM2_IRQn);
USART1 can preempt TIM2 because it has a higher group priority (lower number).
Key Concept: Preemption vs. Sub-Priority

Group (preemption) priority determines whether interrupt B can interrupt a currently-running ISR for interrupt A. If B has a numerically lower group priority, it preempts A. Sub-priority is a tiebreaker only — it determines which ISR runs first when both A and B are pending at the same group level. Sub-priority never causes preemption.

Nesting and Tail-Chaining

Because the NVIC supports priority-based preemption, interrupts can nest: a higher-priority ISR can interrupt a lower-priority ISR that is already running. Each nesting level pushes another stack frame, so stack sizing must account for the maximum possible nesting depth.

Tail-chaining is an optimization that avoids the overhead of unstacking and re-stacking when a second interrupt is already pending as the first ISR finishes. Instead of performing a full context restore followed by a full context save, the NVIC skips both and jumps directly to the next handler. This reduces back-to-back ISR latency from 24 cycles to just 6 cycles on Cortex-M3/M4.

Figure 2.1 — Tail-chaining eliminates redundant stacking/unstacking between back-to-back ISRs.
Deep Dive: Late Arrival Optimization

There is a related optimization called late arrival. If a higher-priority interrupt arrives during the stacking phase of a lower-priority interrupt (i.e., the hardware is still saving registers), the NVIC does not abort and restart the stack push. It completes the stacking, then vectors to the higher-priority handler first, deferring the lower-priority one.

This is safe because the stacking frame is the same regardless of which ISR runs — the eight saved registers are always the same set. The late arrival optimization keeps the latency guarantee intact while handling priority inversion during the stacking window.

The Vector Table

The vector table is an array of 32-bit function pointers stored at the base of the code memory (address 0x00000000 by default, relocatable via the VTOR register). Each entry maps an exception or interrupt number to the address of its handler function.

C
/* Cortex-M vector table (typical startup_stm32f4xx.c structure) */
__attribute__((section(".isr_vector")))
const uint32_t g_pfnVectors[] = {
    (uint32_t)&_estack,           /* Initial stack pointer          */
    (uint32_t)Reset_Handler,      /* Reset                    -15   */
    (uint32_t)NMI_Handler,        /* NMI                      -14   */
    (uint32_t)HardFault_Handler,  /* Hard fault               -13   */
    (uint32_t)MemManage_Handler,  /* Memory management fault  -12   */
    (uint32_t)BusFault_Handler,   /* Bus fault                -11   */
    (uint32_t)UsageFault_Handler, /* Usage fault              -10   */
    0, 0, 0, 0,                   /* Reserved                       */
    (uint32_t)SVC_Handler,        /* SVCall                    -5   */
    (uint32_t)DebugMon_Handler,   /* Debug monitor             -4   */
    0,                            /* Reserved                       */
    (uint32_t)PendSV_Handler,     /* PendSV                    -2   */
    (uint32_t)SysTick_Handler,    /* SysTick                   -1   */
    /* External interrupts (device-specific) start here             */
    (uint32_t)WWDG_IRQHandler,    /* Window watchdog            0   */
    (uint32_t)EXTI0_IRQHandler,   /* EXTI line 0                1   */
    /* ... more entries ...                                         */
};
The first entry is the initial stack pointer, not a handler. Entry index = exception number + 16.
VTOR Alignment Requirement

If you relocate the vector table using the VTOR register (common when running from RAM or with a bootloader), the new address must be aligned to the next power of two that is greater than or equal to the table size. For a table with 128 entries (512 bytes), the base address must be 512-byte aligned. Misalignment causes a hard fault at the first interrupt.

RAM-Based Vector Table for Runtime Patching

Copy the vector table to RAM and set VTOR to point there if you need to change interrupt handlers at runtime — for example, a bootloader that installs application-specific handlers before jumping to the app. This avoids flash write cycles and enables instant handler swaps.

Key Takeaway

The NVIC's three superpowers are deterministic priority resolution, zero-overhead tail-chaining, and automatic context save/restore. Configure priority grouping early in your startup code, assign priorities deliberately (not arbitrarily), and size your stack for worst-case nesting. The vector table is your interrupt routing table — every handler address must be correct or the system hard-faults.

Chapter 3 Writing Safe ISRs

~12 min read
Key question: What rules must an ISR follow to avoid corrupting shared data, and what are the most common mistakes that cause intermittent, hard-to-debug failures?
Prerequisite

This chapter builds on Chapter 1 (interrupt lifecycle) and Chapter 2 (NVIC priority and nesting). You should understand that an ISR can fire between any two instructions in main-context code.

The volatile Keyword

The most critical rule in interrupt-driven firmware: any variable shared between an ISR and non-ISR code must be declared volatile. Without it, the compiler's optimizer may cache the variable in a register and never re-read it from memory, causing main-context code to miss updates made by the ISR.

C
/* BUG: missing volatile -- compiler may optimize away the while loop */
uint8_t data_ready = 0;

void USART1_IRQHandler(void) {
    rx_buffer[rx_head++] = USART1->DR;
    data_ready = 1;  /* ISR sets the flag */
}

int main(void) {
    /* ... init ... */
    while (1) {
        while (!data_ready) {}  /* Compiler may read data_ready ONCE */
        process_data();         /* and spin forever, never seeing 1   */
        data_ready = 0;
    }
}
C
/* FIX: volatile forces the compiler to re-read from memory every time */
volatile uint8_t data_ready = 0;

void USART1_IRQHandler(void) {
    rx_buffer[rx_head++] = USART1->DR;
    data_ready = 1;
}

int main(void) {
    /* ... init ... */
    while (1) {
        while (!data_ready) {}  /* Now re-reads data_ready each iteration */
        process_data();
        data_ready = 0;
    }
}
Key Concept: What volatile Actually Does

volatile tells the compiler: "this variable can change at any time for reasons you cannot see." The compiler must generate code that reads from and writes to the actual memory location every time the variable is accessed — no register caching, no eliding of "redundant" reads, no reordering past sequence points. Note that volatile does not provide atomicity or memory ordering guarantees — it only prevents optimization of accesses.

Critical Sections and Atomicity

A critical section is a block of code that must execute without interruption. You need one whenever main-context code reads or modifies a multi-byte variable that an ISR also accesses. On an 8-bit or 16-bit MCU, even a 32-bit integer read is non-atomic — the ISR can fire between two byte loads, producing a value that is half old and half new (a torn read).

C
/* Safe critical section using PRIMASK on Cortex-M */
static inline uint32_t critical_enter(void) {
    uint32_t primask = __get_PRIMASK();
    __disable_irq();  /* Set PRIMASK = 1, masking all configurable IRQs */
    return primask;
}

static inline void critical_exit(uint32_t primask) {
    __set_PRIMASK(primask);  /* Restore previous state (supports nesting) */
}

/* Usage: */
volatile uint32_t tick_count = 0;  /* Updated by SysTick ISR */

uint32_t get_ticks(void) {
    uint32_t primask = critical_enter();
    uint32_t ticks = tick_count;  /* Guaranteed atomic read */
    critical_exit(primask);
    return ticks;
}
Saving and restoring PRIMASK allows critical sections to nest correctly.

On Cortex-M3/M4 and above, 32-bit aligned reads and writes are naturally atomic (single bus transaction), so you do not need a critical section for a single volatile uint32_t. But any read-modify-write sequence (e.g., counter++) is never atomic and always needs protection.

Keep Critical Sections Short

Disabling interrupts blocks all ISRs, increasing worst-case interrupt latency for every peripheral. A critical section that takes 5 microseconds adds 5 microseconds to the latency of every other interrupt in the system. Never put I/O waits, delay loops, or function calls with unpredictable duration inside a critical section. If you need more than a few instructions, consider a lock-free data structure (ring buffer) instead.

Deep Dive: Lock-Free Ring Buffers

For high-throughput ISR-to-main data transfer (UART RX, ADC samples), a lock-free ring buffer avoids disabling interrupts entirely. The pattern works because the ISR is the sole producer (writes to head) and main code is the sole consumer (writes to tail). Each side only modifies one index, so no critical section is needed — as long as both indices are volatile and the buffer size is a power of two (enabling bitmask wrap-around).

C
#define BUF_SIZE 256  /* Must be power of 2 */
#define BUF_MASK (BUF_SIZE - 1)

volatile uint8_t ring_buf[BUF_SIZE];
volatile uint16_t ring_head = 0;  /* ISR writes here */
volatile uint16_t ring_tail = 0;  /* Main reads here */

/* ISR producer -- no critical section needed */
void USART1_IRQHandler(void) {
    uint16_t next = (ring_head + 1) & BUF_MASK;
    if (next != ring_tail) {          /* Not full */
        ring_buf[ring_head] = USART1->DR;
        ring_head = next;
    }
}

/* Main consumer -- no critical section needed */
int ring_read(uint8_t *byte) {
    if (ring_head == ring_tail) return -1;  /* Empty */
    *byte = ring_buf[ring_tail];
    ring_tail = (ring_tail + 1) & BUF_MASK;
    return 0;
}

Common Pitfalls

After years of debugging interrupt-related failures in production firmware, certain patterns come up repeatedly. Here are the most dangerous, ranked roughly by how often they cause real-world bugs.

Pitfall Symptom Fix
Missing volatile Flag never seen by main loop; works in debug, fails in release Declare shared variables volatile
Non-atomic read-modify-write Counter skips values or corrupts intermittently Critical section or atomic intrinsics
Forgetting to clear the interrupt flag ISR fires in an infinite loop; system hangs Clear the peripheral flag inside the ISR
Too much work in the ISR Other interrupts starved; missed deadlines Set a flag and defer work to main loop or a task
Calling non-reentrant functions from ISR Heap corruption (malloc), garbled output (printf) Never call malloc, printf, or floating-point math in ISRs
Priority inversion High-priority ISR blocked waiting for data from a low-priority one Review priority assignments; use BASEPRI for selective masking
C
/* BAD: Doing too much work in an ISR */
void TIM2_IRQHandler(void) {
    TIM2->SR &= ~TIM_SR_UIF;  /* Clear flag -- good */

    /* DON'T: process an entire FFT in the ISR */
    for (int i = 0; i < 1024; i++) {
        fft_buffer[i] = adc_samples[i] * window[i];
    }
    compute_fft(fft_buffer, 1024);  /* Blocks for hundreds of us! */
    update_display(fft_result);     /* Even worse -- I/O in ISR */
}

/* GOOD: Set flag, defer processing */
volatile uint8_t fft_pending = 0;

void TIM2_IRQHandler(void) {
    TIM2->SR &= ~TIM_SR_UIF;
    /* Swap buffer pointers (fast, ~2 instructions) */
    uint16_t *tmp = adc_active_buf;
    adc_active_buf = adc_fill_buf;
    adc_fill_buf = tmp;
    fft_pending = 1;  /* Signal main loop */
}

/* In main(): */
if (fft_pending) {
    fft_pending = 0;
    compute_fft(adc_fill_buf, 1024);  /* Runs in main context */
    update_display(fft_result);
}
The "set a flag, defer the work" pattern keeps ISRs fast and predictable.
Debug vs. Release Behavior Differences

A classic symptom of a missing volatile: the code works perfectly in debug mode but fails in release. Debug builds typically disable optimization (-O0), so the compiler re-reads every variable from memory anyway. Release builds (-O2, -Os) aggressively cache values in registers, exposing the missing volatile. Always test with your release optimization level.

Key Takeaway

Safe ISR design follows three rules: (1) mark shared variables volatile, (2) protect multi-step accesses with critical sections or use lock-free structures, and (3) keep the ISR body as short as possible — set a flag and defer heavy work to main context. Most interrupt bugs are concurrency bugs, and they are intermittent by nature. If you follow these rules from the start, you avoid the hardest class of embedded debugging.
